# Day-One Decisions: the reasoning and the commands behind S1–S10

Each section: why the gate exists (the observed failure on a real shipped app), then the exact
day-one move. The recurring shape: **every expensive week traces to a decision that was cheap on
day 1 and brutal on day 45.**

## S1 Toolchain pins

Observed failure: a project that started on pnpm, switched to npm to dodge a Metro symlink issue,
then switched back for cloud builds, and hit 7 sequential build failures on the first production
build, several caused by pin drift (a stale tracked `package-lock.json` made the cloud builder run
`npm ci` against `workspace:*` deps; the cloud image's default Node was too old for the pinned
package manager).

Day-one moves:

```jsonc
// package.json
"packageManager": "pnpm@<exact>",      // or npm/yarn: pick ONCE, based on cloud-build support
// eas.json: EVERY profile, not just production
"node": "<exact version ≥ what your package manager needs>"
```

- `git ls-files | grep -c 'lock'` → exactly one lockfile tracked. Gitignore the others by name.
- pnpm only: any package with a required postinstall (licensed component tiers, native codegen)
  goes in `pnpm-workspace.yaml` → `onlyBuiltDependencies` on day 1. pnpm silently skips
  postinstalls otherwise, and the resulting "package is broken" diagnosis wastes a session.
  If a cloud build fails with `ERR_PNPM_IGNORED_BUILDS`, that's this.
- Transitive build-time deps referenced by config files (`babel.config.js` naming
  `babel-preset-expo`) must be **direct** dependencies under strict/isolated node_modules.

## S2 Repo shape

Observed failure: a monorepo flattened to a single package *mid-project, during the production
build crisis*: infra churn stacked on top of debugging, and every path in every doc went stale.

Decide at scaffold: single-package at root (default for a one-app project) or a workspace (only
if a second package genuinely exists on day 1). Write the decision and the native project's path
(`ios/` is a generated prebuild artifact: gitignored, regenerated by `expo prebuild`; config
lives in `app.config.ts`, never edited under `ios/`).

## S3 Component library: all-in or none

Observed failure: an app that started on hand-rolled components, adopted a UI library partway,
then spent the rest of the project fighting it: component anatomy corrected across all surfaces
two months in; the library's styling model (className slots, `style` props silently ignored)
re-learned in session after session; a licensed tier stripped because its postinstall looked
broken; sheet content rendered through the library's portal invisible to the E2E driver, blocking
half the test flows. Meanwhile a comparable app that went all-in on the same library from day 1
shipped seamlessly.

The rule: **commit fully at the start and customize within the library, or skip it entirely.**
All-in means, concretely, in week 1:

1. Install the library *and* any paid tier together; wire its postinstall (S1).
2. Write the styling model into the repo docs: how it's styled (className/classNames/slots vs
   `style`), how it themes, how it composes. One paragraph saves twenty sessions of rediscovery.
3. Compose screen 1 from its primitives. Custom surfaces are built *by composing the library's
   pieces on the library's terms*, never by wrapping library components from the outside with a
   house abstraction (the wrapper becomes the fight).
4. Probe the sharp edges immediately: put a bottom sheet + keyboard + E2E driver through it in
   week 1, while switching is still cheap.

A mid-project partial conversion is the worst of three options: you pay the learning curve and
the retrofit fight simultaneously, and the codebase ends up with two grains.

## S4 Tokens before surfaces

Observed failure: a final pre-launch week dominated by polish churn (easing tokens flipped,
selection colors re-litigated, spacing re-tuned per surface) because the rules weren't set when
the surfaces were built. `mobile-design` owns the token system itself; this gate only enforces
the *sequence*: token source first, screen 1 consumes only tokens, `mobile-audit` LINT green
from the first commit.

## S5 Sheets and keyboard, once

Observed failure: the single largest fix cluster of a shipped app (5 rounds over 2 months, from
day 2 to launch day) traced to two day-2 non-decisions: a bottom sheet rendered inside a
ScrollView, and keyboard avoidance handled per-surface forever after.

Day-one rules:
- **Sheets are siblings of the scroll container, never children.** A sheet inside a ScrollView
  renders inline, not as an overlay, and every fix after that is a workaround.
- **One keyboard-avoidance primitive**, named, owned, used by every input surface. When a new
  surface needs the keyboard, it adopts the primitive; it never hand-rolls. (For the library
  traps: detached sheets ignoring `bottomInset`, `autoFocus` on mount. See
  `mobile-motion/references/gesture-and-scroll.md`.)

## S6 Quality tooling on day 1

Observed failure: tsc-to-zero, ESLint wiring, and a real test dependency all landed on day 60 of
a 62-day project. The cleanup took a focused day *because someone finally did it*; the two months
of accumulated debt made every intermediate session slower and every refactor scarier.

Day one: `tsc --noEmit` exits 0 and stays 0; linter wired with the RN-idiom false positives
triaged (see `mobile-architecture/references/dev-loop.md` §3); test runner installed as a real
dependency (not run from a cache) with one real test; token-lint in the loop. All four are
one-hour setups at scaffold and week-long excavations later.

## S7 Prove the production bundle immediately

Dev builds load JS from Metro and never compile the production bundle, so a whole class of
failures (un-hoisted transitive deps, Hermes rejecting a dependency's dynamic `import()`) is
*invisible* until the first cloud build, where each attempt costs 15+ minutes.

```bash
npx expo export --platform ios   # ~2 min: the exact Metro+Hermes production bundle EAS runs
```

Run it at scaffold, then before every cloud build (`mobile-ship` BUNDLE mode owns the ongoing
gate). If a dependency's ESM build breaks Hermes, pin it to its CJS build with a scoped
`resolveRequest` in `metro.config.js` (`unstable_enablePackageExports: false` for that package
only). Details in `mobile-ship/references/eas-failure-catalog.md`.

## S8 EAS env binding

Observed failure: a first TestFlight build that crashed on launch because `EXPO_PUBLIC_*` vars
inlined as `undefined`: cloud builds do not read local `.env`; only `expo start` does.

Day one: bind every profile to an environment in `eas.json` (`"environment": "production"` etc.),
push vars (`eas env:push production --path .env`; the default path is `.env.local`, so `--path`
matters), and default every dev-only flag OFF in production with an explicit override. Remember
only `EXPO_PUBLIC_*` inline into the JS bundle; server keys stay server-side.

## S9 Compliance scaffolded in week 1

Observed failure: platform sign-in requirements, account deletion, legal docs, and paid-tier
disclosures all built in a single pre-submission day, after the operating log had already
recorded "we keep claiming submission is one release cycle of work and it never is."

Nothing about these is unknown on day 1. Week 1: stub or ticket each item on
`mobile-ship`'s STORE checklist, and schedule submission as **two** release cycles.

The item most often missed: **third-party AI consent.** If user data reaches any outside model,
App Review expects a screen that names each provider and asks before sending. Observed: found
by an audit in the final week before submission, a rejection-level gap. Declining must still
leave a usable app.

## S10 Dev loop

Any native module (gesture handler, Reanimated worklets, Skia, MMKV) means Expo Go cannot run
the app: dev-client + `expo prebuild` + `expo run:ios` from day 1. Add a launch config so agents
and humans start the app the same way. The rebuild-vs-reload rule, the CocoaPods locale crash,
and the E2E preamble live in `mobile-architecture/references/dev-loop.md`.

## S11 Observability live

Observed failures, all from one app's first five months:
- The onboarding funnel was never readable until the month before submission, so the
  onboarding program slipped past launch. Events existed; nothing was looking at them.
- The crash-reporting build plugin broke cloud builds under the project's package manager, so it
  was dropped "for now", and the app went to review with crash reports that arrive minified.
  Solving symbolication on day one costs an afternoon; at submission it costs a release.
- A sibling app shipped a typed event union with no sink at all: events lived in memory and were
  gone on relaunch.

Day one: pick the sink, send one event from a release build and see it land, force one crash
from a release build and read its stack. Write the event dictionary next to the union, with a
test that fails when an event has no row. Log cost per model call from the first call.

## S12 Lifecycle plumbing

Observed failures:
- The notifications plugin in its bare string form omitted the push entitlement and the release
  build crashed. The object form writes it.
- Scheduled push jobs reported success for three months while delivering nothing, because the
  scheduler logged the HTTP call as sent without waiting for a response. Prove delivery from
  the response table, never from the job log.
- A client-side `isPremium` flag gated nothing: declining the paywall meant free forever. Found
  one week before submission.
- Swapping subscription providers mid-project took a week and invalidated the privacy labels.
  A provider-independent entitlement table makes the provider a detail.

Day one: install and configure the notifications module properly (it forces a native build, so
do it before there are thirty screens), create the token table, and create the entitlement table
with a server-side check that everything gated calls. The paywall itself can wait; the gate cannot.
